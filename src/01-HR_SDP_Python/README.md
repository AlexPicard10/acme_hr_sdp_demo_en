# LDP pipeline — HR 360 (Python)

Pipeline `HR_360_Python_<target>` → schema `alp_demo_catalog.acme_hr_en_python`. It implements the
**same logic** as the SQL pipeline [`../01-HR_SDP_SQL/`](../01-HR_SDP_SQL/README.md), written with
the Python API `from pyspark import pipelines as dp`. Both pipelines read the same Volumes
(`acme_hr_en.landing_fr`, `acme_hr_en.landing_be`) and produce tables with the same names, same
columns and same content (check: "SQL vs Python" section of
`../01-HR_SDP_SQL/03-Explorations/hr_exploration.sql`).

```
00-Data-Sources/
  Raw-Employees.py           -> bronze_employees   (create_streaming_table + 2 @dp.append_flow generated by a loop)
  Raw-Absences.py            -> bronze_absences    (same)

01-Employees/
  Employees-Silver.py        -> silver_employees               (@dp.table + @dp.expect* + departments join)
  Employees-Last-Extract.py  -> silver_employees_last_extract  (@dp.materialized_view + Window: row_number / count / lag)
  Employees-Gold.py          -> gold_employees_current         (create_auto_cdc_flow, SCD Type 1)
                                gold_employees_history         (create_auto_cdc_flow, SCD Type 2)

02-Absences/
  Absences-Silver.py         -> silver_absences    (@dp.table + @dp.expect*)
  Gold-Employee-360.py       -> gold_employee_360  (@dp.materialized_view)

utilities/
  ingestion.py               shared Auto Loader function (imported via root_path, not a pipeline source)
```

Each file names its twin SQL file in its header; the detailed business explanations live in the
SQL notebooks.

## SQL ↔ Python equivalents

| Concept | SQL | Python |
|---|---|---|
| Streaming table | `CREATE OR REFRESH STREAMING TABLE t AS SELECT … FROM STREAM(src)` | `@dp.table()` returning `spark.readStream.table("src")…` |
| Materialized view | `CREATE OR REFRESH MATERIALIZED VIEW v AS SELECT … FROM src` | `@dp.materialized_view()` returning `spark.read.table("src")…` |
| Empty target table (for flows) | `CREATE OR REFRESH STREAMING TABLE t;` | `dp.create_streaming_table("t")` |
| Append Flow | `CREATE FLOW f AS INSERT INTO t BY NAME SELECT …` | `@dp.append_flow(target="t", name="f")` |
| Auto Loader | `STREAM read_files('path', format => 'json', …)` | `spark.readStream.format("cloudFiles").option("cloudFiles.format", "json")…load(path)` |
| Pipeline parameter | `'${employees_path_fr}'` | `spark.conf.get("employees_path_fr")` |
| Expectation (warn / drop / fail) | `CONSTRAINT c EXPECT (cond) [ON VIOLATION DROP ROW \| FAIL UPDATE]` | `@dp.expect` / `@dp.expect_or_drop` / `@dp.expect_or_fail` (and `expect_all*` for a dict) |
| Auto CDC | `CREATE FLOW f AS AUTO CDC INTO t FROM STREAM(src) KEYS (k) SEQUENCE BY STRUCT(a, b) STORED AS SCD TYPE 2 TRACK HISTORY ON x, y` | `dp.create_auto_cdc_flow(target="t", source="src", keys=["k"], sequence_by=F.struct("a", "b"), stored_as_scd_type=2, track_history_column_list=["x", "y"])` |
| Window function | `ROW_NUMBER() OVER (PARTITION BY a ORDER BY b DESC)` | `F.row_number().over(Window.partitionBy("a").orderBy(F.col("b").desc()))` |
| Intermediate steps | CTE `WITH typed AS (…)` | DataFrame variables `typed = …` |
| Automatic liquid clustering | `CLUSTER BY AUTO` | `cluster_by_auto=True` |

## When to prefer Python?

- **Reuse**: one ingestion function (`utilities/ingestion.py`) shared by every dataset; flows
  generated by a loop (adding a subsidiary = one entry in `SOURCES`).
- **Testing**: transformations are Python functions, unit-testable on a small DataFrame.
- **Python-only features**: sinks (Kafka, external tables), `foreach_batch_sink`, Auto CDC from
  snapshots, custom data sources.

For a SQL-oriented team and simple declarative transformations, SQL stays more readable: both
languages run on the same engine, with the same performance.
